## 1. 一句话定位

**AEOS 把工程治理做成可编译、可安装、可验证的资产。** 输入是一份结构化、平台中立的工程策略源；输出是各 AI 编程客户端的原生入口、按需知识包、安全的安装生命周期，以及（正在建设的）效果度量。

不变的初衷（v0.1 至今）：核心规则保持 Agent/Prompt 无关，平台差异全部收敛到 Adapter；AEOS 是治理与上下文层，不是 Runtime，不越过宿主的沙箱与审批。

## 2. 竞争格局与差异化

| 项目 | 模式 | 强项 | 与 AEOS 的关系 |
| --- | --- | --- | --- |
| ruler（31+ 客户端） | `.ruler/` Markdown 拼接 → 分发到各客户端；MCP 配置传播；`.bak` 回退 | 覆盖面广、上手极快 | 同步器：分发"任意散文" |
| rulesync（23+ 工具） | 统一源生成 rules/commands/subagents/skills/MCP/ignore；支持 import 与工具间 convert | 特性面最全、双向迁移 | 同步器 + 转换器 |
| GitHub spec-kit（30+ Agent） | 流程脚手架：constitution + `/specify → /plan → /tasks → /implement` 斜杠命令 | 把"过程"做成了可执行命令 | 流程层，与 AEOS 策略层互补 |

AEOS 不与同步器拼客户端数量，差异化在四点，且每一点都有机械保障而非口头承诺：

1. **结构化策略而非散文**：每条规则有稳定 ID、required/recommended 级别、scope、rationale、evidence、可追溯 source，JSON Schema 校验，构建即验证。同步器分发的是文本，AEOS 分发的是"可审计的规则对象"。
2. **上下文预算是硬门**：行数 + token 双预算 gate 在编译期强制执行；知识包按需加载。这直接回应 Chroma "Context Rot" 研究的结论——上下文越长，指令遵循越差。canonical `AGENTS.md` + 指针渲染进一步把全平台安装成本从 ~5.1k token 压到 ~3.5k token（`npm run eval` 实测）。
3. **安装是受管生命周期而非覆盖写**：哈希 manifest、冲突拒绝、强制备份、孤儿 prune、doctor/diff/eject——比 ruler 的 `.bak` 和 rulesync 的重新生成更接近"包管理器"语义。
4. **效果可度量（在建）**：context-cost 已落地，遵循度 A/B 协议已定义（`eval/ADHERENCE_PROTOCOL.md`）。同类工具都没有回答"规则是否真的改变了 Agent 行为"。

兼容策略：不与 spec-kit 争流程——AEOS 的 workflows 未来编译为各平台 Commands/Skills 时，形态与 spec-kit 类似但内容是"治理动作"（review、incident、handoff），两者可共存于同一仓库。

## 3. 分层模型（L0-L4）

```text
L0 策略源     policies/core.json + constitution/ + standards/ + workflows/ + playbooks/ + templates/
                │  （结构化规则 = 真理源；散文 = 解释与细节）
L1 编译       adapters/compiler.js
                │  Schema 校验 → 行/token 预算门 → 平台 renderer（全文 | 指针）→ 确定性哈希
L2 分发       bin/aeos.js CLI（npm 入口）· action.yml（GitHub Action）· 模板 workflow
                │
L3 生命周期   adapters/integrator.js
                │  init / update(+prune) / doctor / diff / eject · install-manifest 所有权语义
L4 评估       eval/
                   context-cost（已落地）· 遵循度 A/B 协议（已定义）· 无头 Agent 矩阵（规划）
```

不变量（在 v2.0 六条之上新增两条）：

7. 每个分发通道（Action、模板、未来的 import）都必须复用 CLI/integrator 的安全语义，不得旁路。
8. 任何新的"始终加载"内容都必须通过预算门；预算上调需要评估数据支持。

## 4. 平台能力矩阵与利用计划

| 平台 | 读 AGENTS.md | 作用域规则 | 命令/技能 | AEOS 现状 → 下一步 |
| --- | --- | --- | --- | --- |
| Codex CLI | 原生（canonical） | 目录级 AGENTS.md 遍历 | — | 全文入口 → 目录级 scoped 入口 |
| Cursor | 原生 | `.mdc` 四类规则（Always/Auto-Attached globs/Agent-Requested/Manual） | — | 指针 → 按 policy.scope 生成 Auto-Attached 规则 |
| GitHub Copilot | 原生（含子目录） | `.github/instructions/*.instructions.md` + `applyTo` glob | 提示词文件 | 指针 → applyTo 分域指令 |
| Claude Code | 可读（CLAUDE.md 更优先） | 目录级 CLAUDE.md | `.claude/commands`、Skills | 指针 → workflow 包编译为 commands/skills |
| Gemini CLI | 未支持 | — | — | 全文入口（保持） |
| Cline | 未支持 | `.clinerules/` 多文件 | — | 全文入口（保持） |
| Antigravity | 自有 `.agents/AGENTS.md` | — | — | 全文入口（保持） |
| ChatGPT/API | n/a（system prompt） | — | — | system 渲染（保持） |

关键洞察：`policy.scope` 字段（all/implementation/design/tools/dependencies/documentation）今天只是元数据；它是通往 Cursor globs 和 Copilot `applyTo` 的现成桥梁——**scope → 文件模式映射**是 renderer 差异化的第一个真实用武之地。

## 5. 从调研借鉴的能力（纳入路线）

- **import**（ruler/rulesync 均有）：`aeos import` 读取存量 `CLAUDE.md`/`.cursorrules`/copilot-instructions，辅助映射为结构化策略草稿。存量项目迁移是最大的采用障碍，此为拆除它的工具。
- **revert/eject**：ruler 有 revert；AEOS 的 eject 语义已更强（manifest 驱动 + 备份），保持。
- **MCP 配置传播**（ruler/rulesync 有）：**明确不做**——凭证与工具接入是宿主与用户的职权，与"策略"边界不同；写入 Non-goals。
- **嵌套规则目录**（ruler nested mode）：暂不做，等 scoped 渲染落地后再评估目录级需求。
- **官方技能分发**（rulesync fetch）：远期，等 workflow 包成为 Skills 后自然获得。

## 6. Non-goals（负面清单）

不做 Agent Runtime、权限沙箱、自主编排器；不做 MCP 凭证/服务器配置管理；不做后台常驻或实时同步（显式 `update` 是特性而非缺陷）；不追求客户端数量榜——只支持能被预算门与生命周期语义认真对待的平台。
